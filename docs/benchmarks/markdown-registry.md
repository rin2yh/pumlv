# Markdown Registry benchmarks

## 再実行・測定条件

```sh
go test ./internal/server -run '^$' \
  -bench '^(BenchmarkRegistry(Update|List)|BenchmarkMarkdownDiagrams)$' \
  -benchmem -benchtime=1s -count=3 -cpu=2
```

2026-11-04（Asia/Tokyo）、Debian 13.6／Linux 6.18.57 amd64、AMD EPYC 9V74、Go 1.26.10。CPU割り当て2 CPU相当、メモリ上限8 GiB、GOMAXPROCS=2。表は3回測定の中央値。プロファイラ・race検出・並行ビルドなし。

`B.Loop`でデータ生成・初期登録を除外し、`ReportAllocs`で割り当てを計測する。入力は見出し・本文・タイトル付きの固定長シーケンス図。Updateは1ディレクトリを登録し、事前変更した1ファイルを繰り返し更新する（読み取り・解析を含み、書き込み・Watcherは除外）。Listはコピー・ソートのみ。HTTP/JSON・PlantUML描画は含めない。CIではベンチマークを実行しない。

## Markdown解析の最適化比較

変更前 `aac4bdf` → 差分走査 `07f1c8e`。同じ環境・既存の `BenchmarkMarkdownDiagrams` で比較した。

| 1ファイルの図数 | ns/op 前→後 | B/op 前→後 | allocs/op（前後同じ） |
| ---: | ---: | ---: | ---: |
| 100 | 208,724 → 210,272 | 241,377 → 241,377 | 2,225 |
| 1,000 | 3,036,540 → 2,139,941 | 2,212,690 → 2,212,688 | 21,128 |
| 10,000 | 132,303,882 → 26,593,507 | 23,064,350 → 23,064,341 | 210,136 |

- 前回位置から改行だけを数え、行番号算出を入力バイト数に対してO(N)、追加状態O(1)にした。Goldmarkと出現順・行番号・タイトル・ソースの仕様は維持。
- 10,000図で約4.98倍高速化（時間79.9%減）。100→1,000→10,000図の時間比は約14.55倍・43.57倍から10.18倍・12.43倍になった。100図では改善を確認できず、割り当て回数も変わらない。
- 別途3秒のCPUプロファイルで、行番号算出の累積サンプル割合は初回75.25%から約0.45%へ低下。残る主な負荷はGoldmark・ソース正規化・割り当て・GC。

生データ: [初回（解析の最適化前を含む）](markdown-registry-results.txt)／[比較用の変更前](markdown-lines-before-results.txt)／[変更後](markdown-lines-after-results.txt)。初回の10,000図は約135.3msで、上表の変更前は再測定値。

## 制約・検証

単一環境・小さな図・競合なし・ページキャッシュが温まった条件であり、性能保証やCIの固定閾値には使わない。多数の個別入力パス、巨大な単一図、並行リクエストは未評価。行番号算出を線形化しても、解析全体の厳密な線形性は保証しない。

`B/op`は累積割り当てで、ピーク・常駐メモリではない。10,000図の解析は約23 MB/回の割り当てと更新ロック内での処理が残り、Listのコピー・ソートやキャッシュ保持量も今回の最適化対象外。

LF・CRLF、入れ子、空・未閉鎖ブロック、対象外ブロック混在の回帰テスト、`make ci`、`make e2e`全6件が成功。[GitHub CIも全5ジョブ成功](https://github.com/rin2yh/pumlv/actions/runs/41682594430)を確認済み。
