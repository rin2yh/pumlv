# Markdown Registry benchmarks

PR #231 のRegistryキャッシュについて、更新・一覧取得・Markdown解析を個別に測定する。初回測定では実装を最適化せず、CIへのベンチマーク実行の追加や固定の性能閾値も設けなかった。開始行番号の算出を最適化した後の比較は、末尾の追記に記載する。

## 実行方法

リポジトリのルートで実行する。

```sh
go test ./internal/server -run '^$' \
  -bench '^(BenchmarkRegistry(Update|List)|BenchmarkMarkdownDiagrams)$' \
  -benchmem -benchtime=1s -count=3 -cpu=2
```

`testing.B` の `B.Loop` により、データ生成・ファイル作成・初期登録・初期検証を計測から除外する。各ケースで `b.ReportAllocs()` を指定する。通常のテストやCIではコンパイルされるだけで、`-bench` を指定しない限り実行されない。

- `BenchmarkRegistryUpdate`: 100・1,000・10,000 Markdownファイル、各10図。単一のディレクトリを登録し、1ファイルの内容を事前に変更する。そのパスへの更新通知が繰り返された場合の `Update` を測る。各呼び出しで実際にファイルを読み、解析・ロック取得・エントリ置き換えを行う。反復中の書き込み、Watcherのデバウンス、初回のディレクトリ走査は含めない。
- `BenchmarkRegistryList`: 同じ3規模、各ファイル10図。キャッシュ済みメタデータのコピーとソートを測る。HTTP配信とJSONエンコードは含めない。
- `BenchmarkMarkdownDiagrams`: 1ファイルに100・1,000・10,000図。見出し・本文・単一行タイトル付きの小さなシーケンス図を繰り返す。各図の長さを揃え、図数の影響を比較する。入力はそれぞれ12,722・127,022・1,270,022 bytes。PlantUMLの描画は含めない。

## 測定環境

- 測定日: 2026-11-04（Asia/Tokyo）
- 実装の基準コミット: `b57fbd0`。これにベンチマークのみを追加して測定。
- OS: Debian GNU/Linux 13.6、Linux 6.18.57、linux/amd64
- CPU: AMD EPYC 9V74 80-Core Processor（仮想環境の表示名）。可視CPU数3、cgroupのCPU割り当ては2 CPU相当、メモリ上限8 GiB。
- Go: `go1.26.10 linux/amd64`。`-cpu=2` でGOMAXPROCSを2に固定。ベンチマーク本体は並列実行しない。
- race検出・プロファイラなしで各ケース1秒以上を3回測定。計測中にテストやビルドを並行実行していない。下表は各指標の中央値。[生の測定結果](markdown-registry-results.txt)も保存する。

### 更新

100〜10,000ファイルで約33〜37µs/回、割り当て数は337/回で一定だった。3回の時間範囲は、100ファイルで33,217〜38,213 ns/op、1,000ファイルで33,226〜37,951 ns/op、10,000ファイルで31,951〜34,858 ns/op。今回の条件では総ファイル数に比例する増加は見られず、小さな差を規模拡大による高速化とは解釈しない。

対象ファイルの読み取りと解析だけを行い、全ファイルを走査しない設計と整合する。ただし登録元は1ディレクトリに固定している。コマンドラインで多数の個別パスを渡す場合は、`getFileEntry` が登録元を調べるコストが加わる。また、読み取りはOSのページキャッシュが温まった状態であり、低速ストレージやコールドキャッシュの測定ではない。

### 一覧取得

ファイル数を10倍にすると、時間は約17倍・約12倍、割り当てバイト数は約10倍になった。コード上、メタデータのコピーは総図数に比例し、ファイルのソートは概ね O(F log F) となる。各ファイルの図一覧スライスを複製するため、割り当て数もほぼファイル数に比例する。解析済みソース本体はListでは複製しない。

1,000ファイルで約0.45ms・0.57 MB/回、10,000ファイルで約5.4ms・5.68 MB/回。大量ファイルで一覧取得を高頻度に行う場合は、一時割り当てとGC負荷が懸念になる。これらはList単体の値であり、API全体の応答時間ではない。

### 解析

100→1,000図で時間が約14倍、1,000→10,000図で約45倍になった。割り当てバイト数・回数は概ね図数に比例するが、処理時間はこの範囲で線形に収まらない。

10,000図について別途3秒のCPU・割り当てプロファイルを取得した。CPUサンプルの75.25%は、開始行を算出する `bytes.Count(data[:block.Info.Segment.Start], ...)` に対応していた。各ブロックで文書先頭から数え直すため、各図のサイズを固定すると、この部分の累積走査量は図数に対して二次的に増える。割り当てプロファイルではgoldmarkのAST・行セグメントと、図のソース正規化・結果スライスの生成が主な要因だった。プロファイルの値は上表の中央値には含めていない。

再現例:

```sh
mkdir -p work
go test ./internal/server -run '^$' \
  -bench '^BenchmarkMarkdownDiagrams/diagrams=10000$' \
  -benchmem -benchtime=3s -count=1 -cpu=2 \
  -cpuprofile=work/markdown.cpu -memprofile=work/markdown.mem \
  -o work/server-bench.test
go tool pprof -list=markdownDiagrams work/server-bench.test work/markdown.cpu
go tool pprof -top -alloc_space work/server-bench.test work/markdown.mem
```

## 初回測定時の判断と限界

今回の測定から、総ファイル数を理由にUpdateを最適化する根拠は得られなかった。現時点では実装を維持し、必要なときにこのベンチマークで比較する。10,000図を含むファイルを頻繁に更新する運用が必要なら、開始行算出の繰り返し走査を優先して改善する根拠がある。解析は更新処理の直列化ロック内で行われるため、このような重いファイルは他の更新を待たせる可能性がある。

`B/op` は1操作あたりの累積割り当てであり、ピークメモリやRegistryが保持する常駐メモリ量ではない。図のソースをキャッシュする分の保持メモリは、全ファイルの図数・ソース長に応じて増える。1回の解析で、1,000図では累積約2.21 MB、10,000図では約23.06 MBを割り当てる点にも注意する。多数の長いPlantUMLブロックでは、保持メモリ・GC・更新の待ち時間を実際のデータで追加確認する必要がある。

これは単一環境・固定内容・競合なしの測定であり、巨大な単一図、並行リクエスト、ブラウザ描画、ファイル監視の配信遅延は評価していない。3回の中央値は信頼区間や性能保証ではなく、環境間の絶対値比較やCIの合否閾値には使わない。

## 追記: 開始行番号の算出を差分走査に変更

2026-11-04（Asia/Tokyo）に、変更前の `aac4bdf` と、同コミットの行番号算出だけを差分走査にした実装を比較した。初回測定の結果・生データは上記に残している。今回も同じ環境（Debian 13.6、Linux 6.18.57、AMD EPYC 9V74、Go 1.26.10、CPU割り当て2 CPU相当、メモリ上限8 GiB）で、同一の `BenchmarkMarkdownDiagrams` と入力を使用した。

### 変更内容

GoldmarkによるASTの走査順は維持し、前回の走査位置と行番号を関数内の2変数で保持する。対応ブロックごとに `data[scanned:start]` の改行だけを数え、走査位置を進める。対象外のブロックや本文を挟んでも、その区間全体を次の計数に含める。blockquote・リスト内の対応ブロックも文書順に処理するため、区間は重ならず、行番号算出の総走査量は入力バイト数 B に対して O(B)、追加状態は O(1) になる。行位置テーブルや新たなキャッシュ・依存ライブラリは追加していない。

### 比較方法と結果

変更前と変更後で、以下のコマンドをそれぞれ実行した。データ生成・初期検証の計測除外や `ReportAllocs` は既存ベンチマークのまま。プロファイラ・race検出は使わず、他のビルドやテストと並行実行していない。各指標は3回の中央値。

```sh
go test ./internal/server -run '^$' -bench '^BenchmarkMarkdownDiagrams$' \
  -benchmem -benchtime=1s -count=3 -cpu=2
```

| 100 | 差分走査 | 210,272 | 241,377 | 2,225 |

10,000図では約132.3msから26.6msへ短縮し、約4.98倍の高速化（処理時間79.9%減）となった。1,000図は約29.5%短縮した。100図は約0.7%増で、今回の3回測定から小規模での改善・悪化を断定しない。割り当て回数は全規模で同一、バイト数の差も0〜9 B/回に収まり、メモリ割り当てを減らす変更ではない。

100→1,000→10,000図と増やした際の時間比は、変更前の約14.55倍・43.57倍から、変更後は約10.18倍・12.43倍になった。この入力と測定範囲では、全体の増加傾向も図数比例に近づいた。ただし解析全体の厳密な線形性を保証するものではない。10,000図の実測範囲は変更前128.95〜135.76ms、変更後22.27〜29.07msであり、中央値も環境の影響を受ける。

### CPUプロファイルと残る負荷

変更後の10,000図で、上記と別に `-benchtime=3s -cpu=2 -cpuprofile=...` を指定してプロファイルを再取得した。この実行の測定値は約25.78ms/回で、上表の中央値には含めていない。開始行算出の行に対応する累積サンプルは20ms／全4.48s（約0.45%）となり、初回プロファイルの75.25%を占めていた繰り返し走査は主な負荷ではなくなった。主な負荷はGoldmarkの解析・AST生成と、ソース正規化・割り当て・GCに移っている。CPUサンプルの割合は経過時間の割合ではない。

1回の10,000図解析で累積約23.06 MB・210,136回の割り当てが生じる点と、Registry更新の直列化ロック内で解析する点は残る。常駐キャッシュ量、Listのコピー・ソート、HTTP/JSONやブラウザ描画は今回の最適化対象ではなく、それらに同じ改善率を適用することはできない。初回測定と同様に性能保証やCIの固定閾値は設けない。

### 仕様と回帰検証

LF・CRLFそれぞれで、本文・対象外言語・外側のコードブロックに含まれるフェンス・blockquote・リスト内の空ブロック・複数行タイトル・EOFの空の未閉鎖ブロックを混在させたテストを追加した。出現順・開始行番号・タイトル・正規化済みソースが期待値と一致することを検証している。既存の抽出テストも成功した。

差分走査導入後の `make ci`（フロントエンド単体163件・ブラウザUI30件・Go race検出付きテスト・型チェック・lint・生成を含む）と `make e2e` 全6件が成功した。ベンチマーク本体とCI設定は変更していない。
